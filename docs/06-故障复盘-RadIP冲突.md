# 06 · 故障复盘：Rad:IP conflict（2026-11-19 ~ 11-20）

## 1. 现象

1. 玩游戏中网络突然中断；
2. 重启后无法上校园网，手动登录门户报 **`中国联通认证失败：Rad:IP conflict !`**；
3. 已认证状态下**一插网线就整个断网**，拔掉网线（改用手机热点）反而正常。

## 2. 时间线与证据

| 时间 | 证据 | 说明 |
|---|---|---|
| 11-19 21:32 / 21:44 / 22:41 / 22:52 | 日志四次「判定假在线：下线旧会话并重新登录」 | 客户端每次执行 logoff + 重登，会话被反复拆卸 |
| 11-19 22:57 | 状态页显示 `已在线：CA-**60` | 该 IP 上挂着一条**不属于本账号**的会话 |
| 11-19 22:58 起 | 登录响应 `td.errormsg` = `Rad:IP conflict !` | 真实错误；同时页面被重画并附带 checkcode 字段 |
| 11-20 07:37 | v1.3.0 启动：`登录结果: IpConflict` + 原文入库 | 修复生效，正确识别并长间隔等待 |
| 11-20 12:39 | 同一 IP `10.100.2.125` 登录 **Success** | 冲突约 5 小时后自行消失 |
| 11-20 12:39 | `ipconfig`：以太网 10.100.2.125（DHCP） | **IP 全程未变** |

决定性推论：IP 从头到尾都是 `10.100.2.125`，因此**不是局域网地址冲突**，而是
**运营商 RADIUS 上该 IP/账号的陈旧会话未释放**，直到超时老化才恢复。

## 3. 根因（按责任层拆开）

### 3.1 根因一：RADIUS 侧会话未释放（外部）

游戏断线/异常下线时，NAS 没收到 Accounting-Stop，运营商的 RADIUS 仍认为该 IP 在线。
此后同 IP 的新登录一律被判「IP conflict」。这类会话的超时是以**小时**计的（本次约 5 小时），
所以「早上不行、中午自己好了」正是它的典型表现。

### 3.2 根因二：客户端反复下线重登，把会话打乱（内部，主责）

v1.1.0 的「假在线自愈」在 21:32~22:52 触发 4 次，每次 `logoff` 后 2 秒内重登。
短时间内反复拆卸/重建会话，是制造 RADIUS 陈旧绑定的直接推手。

误判来源：假在线判定依赖 `connect.rom.miui.com/generate_204` 等**需要 DNS** 的探测点，
校园网 DNS 抖动时 HTTP 探测失败，但实际上外网是通的 → 误判 → 自愈 → 越修越坏。

### 3.3 根因三：失败被误分类，重试反而续命惩罚（内部）

旧版分类器看到响应里有 `checkcode` 字段就判 `CaptchaNeeded`，而门户**每次登录失败都会把整张
表单连验证码框重画一遍**，于是：

- 真正的 `Rad:IP conflict` 被掩盖，用户看到的是「需要验证码」；
- 判定为验证码后每 5 分钟重试一次，每次都失败，**持续触发门户的验证码惩罚**，形成死循环。

### 3.4 现象四：插网线就断网（系统层）

手机热点 + 网线同时在位时，Windows 选网线为默认路由（网线跃点 1 / 热点 50），
而网线恰好未认证 → 全部流量走死路 → 热点明明可用也上不了网。

## 4. 修复（v1.3.0）

| 问题 | 修复 |
|---|---|
| 错误被验证码字段掩盖 | 优先解析 `td.errormsg` 原文；`Rad:IP conflict` 独立成 `IpConflict` 结果；`checkcode` 字段不再参与失败判定 |
| 失败后疯狂重试 | IP 冲突固定 5 分钟间隔 + 一次性处置指引（气泡可点击打开门户） |
| 验证码死循环 | 暂停后只观察状态页；删除「登录页无验证码就自动重试」逻辑；「立即检测」可手动恢复 |
| 假在线误判 | 新增**免 DNS 的 TCP 直连探测**（223.5.5.5 / 119.29.29.29:443）；阈值 2→3 次；两次自愈间隔 ≥10 分钟 |
| 报错文案乱码 | 响应解码改为「严格 UTF-8 试解，失败回落 GB2312」 |
| 回归保障 | 用本次真实响应做脱敏夹具，新增 2 项测试；全量 60/60 |

## 5. 用户侧的正确处置顺序

1. 关掉手机热点（同一时刻只保留一个出口）；
2. 插网线，浏览器打开门户，有验证码就填；
3. 若报 `Rad:IP conflict`：点「断开网络」后重登；仍不行就等 10~30 分钟（本次实际约 5 小时）；
4. 想立刻换 IP：管理员 CMD `ipconfig /release` → `ipconfig /renew`；
5. 超过 30 分钟仍报：打 029-85310558，请其清除该账号/IP 的 RADIUS 会话。

想避免「插网线抢默认路由」：网卡属性 → IPv4 → 高级 → 取消「自动跃点」并填 `9999`。

## 6. 教训

1. **对运营商会话的下线/重登必须极其克制**：这是有副作用的写操作，不是幂等的探测。
   原设计把「自愈」建在别人的会话表上，代价由用户承担。
2. **健康检查要选不依赖 DNS 的方式**：DNS 是最容易抖动的一环，用 IP 直连 TCP 才代表「出口真的通」。
3. **判定错误类型要读门户原话**，不要用页面结构（如某个字段存在与否）去猜原因。
4. **失败后的重试策略要区分「重试有意义」和「重试有害」**：IP 冲突、验证码、密码错误都属于后者。
